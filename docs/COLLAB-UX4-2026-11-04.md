**偏差 1｜44px 只在 ≤560 生效 —— 采纳，已改为按输入设备而非视口判定**

- 你的实测正确：768px 下 chip = 37.8px（`height:44px` 被包在 `max-width:560px` 内）。
- 判定：UX-4 目标是"触控目标 ≥44"，约束对象是**输入方式**而非视口宽度，触屏笔电/平板在 768–1024 下同样会点不中，所以按视口切是口径错误。
- 处置：新增独立媒体查询 `@media (pointer: coarse)`，与宽度无关地保持 `height/min-height/min-width:44px`；桌面细指针（fine）维持 37.8px 紧凑态不再改动观感。
- 复算：`Emulation.setTouchEmulationEnabled` 模拟触屏，768px 下 `matchMedia('(pointer: coarse)')` = true，chip 实测 **44.0×5**；同一视口关触屏仍 37.8px，双向可控。

**偏差 2｜481–560px 假渐隐 —— 视觉上不成立，但你的读法点出了真实隐患，已加固**

- 我端实测 500 / 540 / 560 三档：`filters` 类名仅为 `filters`（无 `fade-l/fade-r`），`--fade-r` 计算值 **0px**，`mask-image` 梯度终点为 `100%` 而非 `calc(100% - 22px)` → 无可见渐隐。你大概率读到的是静态 CSS 中的固定声明。
- 但隐患真实：`mask-image` 恒挂在 `.filters` 上，只是靠变量为 0 兜住效果，任何人读 CSS 都会得出"挂了 22px mask"的结论，也容易在后续改动中被改坏。
- 处置：把 `mask-image` 与 `--fade-*` 一并移入 `.filters.is-scrollable`，**只有 JS 判定确实可横滚时才存在 mask**（`is-scrollable` 由 `scrollWidth - clientWidth > 2` 计算）。
- 复算：500/540/560/580 四档 `mask-image` 实测 **none**；375 溢出态仍 `fade-r → 22px` 正常，滚到底翻 `fade-l`。

**偏差 3｜"480 断点密度"实际 540 才双列 —— 成立，且顺带发现更严重的一处挤压**

- 根因两层：①我写的 `@media (max-width:480px)` 里 `grid-template-columns:1fr` 是**冗余声明**（基础 `minmax(220px,1fr)` 在 480 以下本就单列），该断点实际只改了 `gap`；②540–600 区间由 `auto-fill` 接管成 2 列，但卡宽被压到 **193.5px**（540 实测），比任何设计意图都窄。
- 处置：删除 480 断点，改为 `@media (max-width:600px) { grid-template-columns:1fr; gap:12px }`，把"单列"的边界一次钉在 600，避免 540–600 的挤压态与 481–539 的 `gap:16` 中间态。
